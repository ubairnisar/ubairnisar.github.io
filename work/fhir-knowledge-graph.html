Documents into a FHIR knowledge graph

ADONUT turns a scanned medical document into structured JSON. This pipeline goes one step further: it reads that JSON and builds a knowledge graph, not a document graph. The only nodes are real-world entities (a patient, a practitioner, a specimen, a condition, an order) joined by real HL7 FHIR relationships, ready for Neo4j and RDF tools.

Problem

Clinical data on forms is scattered: a patient's name in a header, the ordering physician in a footer, a diagnosis code with no name next to it, a lab panel that continues on a later page. LLMs extracting this will happily invent fields, duplicate the same person, and link things with relationships that don't exist in HL7.

Approach

Let the model reason, but never trust it on structure. Types come from HL7's live resource list, properties from each type's real element list, values are validated with HL7's official FHIR models, codes are grounded in UMLS, and every relationship is re-checked before it is written.

Result

One deduplicated graph per document that only says what FHIR allows it to say: entities merged across pages, fields topped up but never overwritten, and outputs that load straight into Neo4j or any RDF store.

What comes out

Real-world entities, joined by real FHIR edges.

    Guardrails

    The model reasons. The spec decides.

    01

    Types from HL7, live

    The resource type list is read from HL7's published spec, so it can't drift. Anything else falls back to Basic.

    ✓ no invented types
    02

    Schema built per type

    Each entity's output schema is generated from its type's real elements, so a field HL7 doesn't define can't even be written.

    ✓ no invented fields
    03

    Official FHIR validation

    Values are reshaped into proper FHIR data types (coded concepts, quantities, dates, repeating fields) and validated with HL7's official FHIR models.

    ✓ structurally valid FHIR
    04

    Repair from real errors

    Failures go back to the model as the actual validation message, for only the failing fields, at most twice. No endless loops for data that isn't there.

    ✓ bounded cost
    05

    Codes grounded in UMLS

    A bare "Z00.129" or "FISH" is looked up in the National Library of Medicine's UMLS across ICD-10, SNOMED CT, LOINC, RxNorm, CPT and HCPCS, never guessed from memory.

    ✓ no hallucinated codes
    06

    Predicates re-checked

    Every relationship is verified against the source type's real reference elements before it's written, even if the model says it called the tool.

    ✓ 0 invented edges
    07

    Dedup without data loss

    The same person in a letterhead and a footer becomes one node. New mentions only fill empty fields; existing values are never overwritten.

    ✓ one node per real entity
    08

    Budgets and metering

    Each model call has a cap on lookups, entities are processed in parallel, and usage is tracked across every call.

    ✓ predictable cost
